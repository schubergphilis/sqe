**STATUS 2026-09-16 (al): Ranger access policies gate Hive-root tables, deny by default (`feat/ranger-hive-access-default-deny`).** Designing the company rollout (Okta groups in the JWT, Ranger for the model, Glue root read with a Fargate task role) surfaced the inversion: SQE read only mask and row-filter policies from the Ranger `hive` service, because object-level access is Polaris's job for Iceberg, so with no Polaris in front of a Glue root every table was open to every authenticated user until someone wrote a mask, and a new Glue table was exposed the moment it appeared. `RangerStore` now parses `policyItems`/`denyPolicyItems`/`allowExceptions`/`denyExceptions` and, for a namespace whose first component is a registered Hive root, requires an enabled access policy granting `select`/`all` (deny items win, exceptions carve out, `column` must be `*` or absent for table access, Ranger's `public` group matches everyone); no grant = the existing deny-all sentinel, so listings, `SHOW CREATE TABLE`, `information_schema`, MCP tools and `SELECT` all read "table not found" through the plumbing that already existed. Iceberg namespaces are untouched. `[policy.ranger] hive_access_policies` (default true) turns it off; the coordinator logs which way it is wired at startup; the group-only-item warning now counts access items and skips `public`. Not modelled: `policyPriority` override policies, column-level access decisions (grant the table, mask the columns). Verified: 292 sqe-policy lib tests (10 new), clippy clean on sqe-core/sqe-policy/sqe-coordinator. Not measured against a live Ranger yet; the manual check is one allow policy on `<root>.<database>` for a group, then `SHOW TABLES` as a member and as a non-member.
