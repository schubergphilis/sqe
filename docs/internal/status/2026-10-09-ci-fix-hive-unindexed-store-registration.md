**STATUS 2026-10-09 (ci): unindexed Hive tables read with their own `sqe.secret` again (`fix/hive-unindexed-store-registration`).** Since 2026-09-02 (d3938876, gzip detection), loading an unindexed Hive table built the store for its `sqe.secret` but never registered it on the session runtime. The compression block replaced the `register_object_store` line. `ListingTable` resolves its store from that registry at scan time, so these scans read with whatever the registry held for the bucket, normally the engine's own credentials. Affected: every unpartitioned table, and partitioned tables with neither a partition index nor projection. The path check in `store_for` and the one-secret-per-bucket claim kept running; only the credential that read the data was wrong. Where the engine's credentials could not reach the bucket, the table read as zero rows without an error. The registration is restored after the bucket claim. `an_unindexed_table_reads_through_its_secrets_store` (hive_provider_test) gives the secret's store a filesystem view the default store lacks, and returned 0 rows instead of 1 before the fix.
