**STATUS 2026-09-17 (ba): the Glue database scope, hardened (`feat/glue-database-scope-hardening`).** The ask was a command-line way to select which databases a Glue-backed MCP server exposes; it already existed as `--glue-database a,b` / `[[hive.roots]] databases = [...]` and worked live (`SHOW SCHEMAS FROM glue` listed only the two named, a table elsewhere was "not found"). Two gaps closed: the scope compared case-sensitively against Glue's lower-cased names, so `--glue-database Claude` listed a schema no query could resolve (now folded, trimmed, deduplicated; `database_blocked` compares case-insensitively); and a misspelt name was served as an empty schema forever (now each scoped name is checked with `GetDatabase` at the first listing, a missing one is a WARN and not listed, a Glue call that fails leaves it served unverified). Docs on three pages say what this is: a visibility scope shared by every caller of the endpoint, not per-user authorization. Found while verifying and NOT fixed here: `glue.information_schema.tables` on a Glue root returns the system catalog's schemas (jdbc, metadata, runtime) and zero Hive tables, another face of #664/#665; the issue could not be filed because the GitLab API was returning HTML error pages, file it first thing. NEXT, in the order the user set: (1) Okta in front of the MCP endpoint, which is the existing `bearer_token` provider with Okta's JWKS/issuer/audience and `mcp.auth.mode = "oauth"` (the anonymous flag then becomes refused by config validation, as designed), plus the `oauth_scopes` mapping for `sqe:mcp:read`; (2) the Ranger engine for per-user table access on the Glue root, where a Hive table is readable only after a Ranger access policy grants `select` on `<root>.<database>`, so the database scope becomes the coarse fence and Ranger the per-user gate. Neither needs new engine code to start; both need a config file instead of the flag-only path.
