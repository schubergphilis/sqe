**STATUS 2026-09-16 (ap): the Glue metadata path behind the MCP crawler (`perf/mcp-glue-metadata-path`).** A timed sweep of every MCP read tool against a Glue database on the release build found three costs that were not the data: (1) every `SHOW COLUMNS`, `SHOW STATS` and `SHOW CREATE TABLE` on a Hive root fetched the manifest from Glue again (60 to 80 ms per statement, `GetTable`) while the planner answered the same table from its cache, so the DDL handler now reads through the same three-tier cache (`manifest_cached`, mirroring `manifest_for`); (2) `describe_schema` asked `information_schema.tables` for the table kinds, which enumerates every database of the catalog (135 databases, 12.6 s cold for one call), so `SHOW VIEWS FROM <catalog>.<schema>` exists (classifier variant, Hive root from manifests, Iceberg from REST `list_views`) and the tool uses it; (3) `search_tables` ran one `SHOW TABLES` per database serially (135 × ~110 ms = 17 s), now eight in flight in schema order. Also: Hive `SHOW STATS` reports the planner's listed byte size when Glue carries `totalSize = -1` (every Trino/Athena-written table does). Measured before: describe_schema cold 23.9 s / warm 6.0 s, search_tables 17.3 s; after: see the MR. What remains is the data path: each `EXPLAIN` or `SELECT ... LIMIT 1` on a Glue table lists its S3 prefix on every plan (DataFusion's `ListingTable`, list-files cache disabled since #363), ~500 ms warm.
