**STATUS 2026-09-18 (bc): the limiters answer like rate limiters (`feat/mcp-rate-limit-429-retry-after`).** Fifteen parallel metadata calls from one agent hit the pre-auth limiter (10 per minute per (peer, bearer), burst = rate) and got a bare `{"error":"rate_limited"}` with no `Retry-After`; the client gave up. Now: `rate_limit.auth_burst` (default 20) sizes what one (peer, principal) may present at once, sustained rate unchanged (governor `allow_burst`); the MCP pre-auth 429 carries `Retry-After` (60 / `auth_attempts_per_minute`, rounded up: the bucket's refill interval, the longest a client can have to wait, since the auth error itself carries no time) and a body naming the limiter, the 60 s window, the wait and both knobs. The query and metadata limiters return a `RateLimitDenial` (limiter, knob, exact wait from governor's `NotUntil`) rendered as `ResourceExhausted` text ending in `retry after {n}s`; an MCP tool denial adds `structuredContent {error: rate_limited, retry_after_seconds}`. Tests: twelve presentations of one bearer pass at the defaults and the burst is finite; the 429's status, header and body; the structured tool denial. Configuration reference lists every knob and its env name.
