**STATUS 2026-09-16 (ar): a dead `/mcp` listener is no longer a live PID (`fix/mcp-listener-supervision`).** The sqe-semantic sidecar saw `POST /mcp` stop answering (curl exit 000, no TCP accept) twice on 2026-09-16 after 30 to 60 minutes of idle time while `pgrep sqe-server` still listed the process. The code allowed exactly that: in `--mcp-only` mode `main` only awaits a signal, and the listener was a detached `tokio::spawn` whose `JoinHandle` was dropped, so an accept-loop exit or panic left nothing running and nobody told. Now `start_mcp_server` binds first (reporting the bound port, so port 0 works in tests), runs the serve loop under `supervise_listener` (ERROR log on return, error or panic; an `AliveGuard` clears the liveness flag on any exit including abort), and returns the task; `sqe-server` keeps the handle in `watch_mcp_listener`, which flips readiness and exits 70 (`EX_SOFTWARE`) when the task ends. `/healthz` answers `503 mcp listener down` and `/readyz` carries `checks.mcp` for a dedicated port. Tests: healthz/readyz on a dead flag, the watcher's exit path, and `tests/it/mcp_listener_supervision_e2e` (real TCP, initialize + tools/call, idle 65 s past the 60 s session-context TTL, again, then abort clears the flag and closes the port). Root cause of the original hang is still open: a repro instance of the release build has idled with `RUST_LOG=debug` and a one-minute probe since 16:49 and has answered every probe so far; if it reproduces, `idle.log` in the session scratchpad has the last debug lines before it.
