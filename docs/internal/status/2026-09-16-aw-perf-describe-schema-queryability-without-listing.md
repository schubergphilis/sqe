**STATUS 2026-09-16 (aw): `describe_schema` queryability without touching storage (`perf/describe-schema-queryability-without-listing`).** With `include_queryability` the tool planned `EXPLAIN SELECT * FROM t LIMIT 1` per table, and planning a Hive table lists its S3 prefix (DataFusion's `ListingTable`, list cache off since #363): half a second warm, one to two seconds cold, a hang with expired credentials; 40 tables cost 5 s and a 25-table page hung. `LIMIT 0` gives the same answer for what a crawler asks: DataFusion resolves the table (that is where `resolve_format`, the SerDe allow-list, the location boundary and the column typing run, and where a view's SQL is planned) and eliminates the zero limit before physical planning, so no scan and no listing. A provider test on the counting store pins it: after the one facts listing, `EXPLAIN ... LIMIT 0` adds zero LIST calls while `LIMIT 1` adds one. What still lists cold is the size-only statistics listing in `table()` (once per manifest version, cached 60 s), so a first crawl of 618 tables pays 618 LISTs at eight in flight (about half a minute) and the second one pays none. Next lever if that matters: a TTL-bounded DataFusion list-files cache for Hive roots, invalidated on SQE's own writes, so `SELECT`, `sample_rows` and `EXPLAIN` within the TTL skip the LIST too; not a startup warmer over every table, which would list 618 prefixes a minute for tables nobody reads.
