**STATUS 2026-10-07 (by): row-filter error oracle closed, scan pruning kept (`fix/row-filter-error-oracle`, carries !1316, #805).** The optimizer merges a caller's WHERE with the policy row filter into one conjunction, and AND evaluates its right side over the whole batch unless few rows pass, so `WHERE 1 / (id - 2) = 1` could raise an error from a hidden row. !1316 read every row-filtered column through `CASE WHEN <row filter> THEN col END`, which cost all pruning. Now `sqe-policy/src/leakproof.rs` classifies caller expressions the optimizer can move below a row filter (filters, join conditions, scan filters, projection / group-by / window-partition expressions). Comparisons, `IN`, `BETWEEN`, constant-pattern `LIKE`, boolean logic and lossless casts are leakproof. Arithmetic, functions, subqueries and casts that can fail are not, and neither is any comparison whose coercion casts a column lossily. The guard is only added when the plan holds a fallible expression (a plan-wide switch, because aliases hide which scan column a predicate reads). A fallible predicate already pushed into a scan (a view body) is lifted above the guard. `write_predicates` recognises the guard by its shape, so a mask directly over a row filter is still extracted. **Open:** remaining items tracked in #805, including an SF1 A/B of guarded queries.
