**STATUS 2026-10-20: `CAST(.. AS TIMESTAMP WITH TIME ZONE)` keeps the zone; Trino clients get `<local> <zone>` (`fix/timestamptz-cast-zone`, #848).**

Every SQE session now runs in UTC: `sqe_catalog::session_tuning::ENGINE_TIME_ZONE = "+00:00"` is set in `engine_session_config()`, in the view-planning context (`schema_provider.rs`) and in the worker session (`sqe-worker/src/runtime.rs`). Without a session zone, DataFusion typed `CAST(x AS TIMESTAMP WITH TIME ZONE)` as a timestamp without a zone. `to_timestamp*` is zoned now too, typed `Timestamp(*, "+00:00")` like a scanned Iceberg `timestamptz` column. An offset in the cast text is applied, and the value is stored in UTC. Trino keeps the offset, but Arrow has one zone per column. Comparing a timestamp column with a zoned literal still casts the literal, not the column, so pruning is unaffected (`zoned_literal_filter_leaves_the_column_uncast`).

Second gap, found while checking the client side: the Trino encoder sent zoned values as Arrow writes them (`2024-01-02 01:04:05.000000Z`). The Python client splits the zone off at a space, and SQE's own `decode.rs` expects `<local> <zone>`, so values now go out as `... UTC` / `... +02:00`.

Third gap, found by the integration test: on main, any filter on a V3 nanosecond timestamp column failed. First, `pruning_stats.rs` `datum_to_scalar` turned `long` bounds into `Int64` statistics unless the column was a microsecond timestamp, so planning failed with "Interval data types must be compatible ... lhs:Int64, rhs:Timestamp(ns, ...)". It now returns only the column's own type, widening `int -> long` and `float -> double` bounds for promoted columns, and gives `None` for anything else. `time` columns had the same Int64 mismatch. Second, `expr_to_predicate.rs` sent every nanosecond literal to Iceberg as a microsecond `timestamp`, which can't bind to a `timestamptz_ns` column. It also passes `CAST(col AS ...)` through as `col`, and Iceberg binds a timestamp literal by reinterpreting the number, so a unit mismatch would have pruned with a value 1000x off. The converter now gets the scan schema (`convert_filters_to_predicate_for`, `is_filter_pushdown_supported(expr, schema)`), and `datum_for_column` converts each timestamp literal to its column's unit and zone. When the conversion isn't exact (a sub-microsecond literal on a microsecond column, or a ns literal on a column of unknown type), that conjunct is not pushed down. That is safe because pushdown is `Inexact`.

Fourth gap, found while reviewing the third: the `Expr::Cast` arm passed `CAST(col AS t)` through as `col` for any cast. Probed on the old arm, `CAST(f AS INT) = 3` (REAL), `CAST(x AS INT) = 3` (DOUBLE), `CAST(s AS INT) = 3` (string) and `CAST(ts AS DATE) = DATE '2024-01-02'` all failed the query with "Can't convert datum from int type to float type" and similar. `cast_is_exact` now allows only casts that keep every value: same type, integer widening, string to string, and a timestamp with the same or a finer unit and the same zone (the UTC spellings count as one). Floats are excluded. Any other cast is not pushed down.

Found, not part of this MR: DataFusion 55.2's physical `unwrap_cast_in_comparison` (`datafusion-physical-expr/src/simplifier/unwrap_cast.rs`) rewrites `CAST(d AS INT) = 3` on a `DECIMAL(10, 2)` into `d = 3.00` without checking that the cast is lossless, so `d = 3.25` is not counted. It returns 0 rows even on `VALUES`, without any Iceberg table; a DOUBLE column is not affected. This is a wrong-results bug in DataFusion, worked as the next branch.

Not changed: SQE's `now()` / `current_timestamp` / `localtimestamp` UDFs still return a timestamp without a zone (`sqe-trino-functions`, `TrinoNow`). In Trino, `current_timestamp` has a zone. Making it zoned would turn CTAS and dbt snapshot columns built from it into `timestamptz`; left for the user to decide.
