**STATUS 2026-10-08 (cc): `ON` keys spanning cross-joined relations are kept (`fix/join-key-spanning-cross-join`, #806, apache/datafusion#26058).** DataFusion 55.1's `eliminate_cross_join` pools every inner join's `on` pairs and rebuilds the tree greedily. It drops a pair it cannot place: one whose side reads two relations that were joined without an equi-key, such as `a CROSS JOIN k JOIN b ON b.t = a.t AND b.id = a.x + k.k` (42 rows instead of 2). Placement depends on the greedy leaf order, so even keys over equi-joined relations can be dropped (`b JOIN (a JOIN k ON a.id = k.id) ON b.t = a.t AND b.id = a.x + k.k`). Keys written in `WHERE` were never affected. `engine_context` (coordinator, `sqe-cli` embedded, Hive view planning) now swaps the rule for `sqe_catalog::eliminate_cross_join`: a copy of the 55.1 source that puts every unplaced `on` pair back on top as a filter, next to the join filters. A NULL-safe join gets `IS NOT DISTINCT FROM`. That is the fix proposed for upstream. A plan with no unplaced pair is exactly what upstream builds; a test pins this for placed keys, including one that spans two equi-joined relations. A pre-rule that moved every multi-leaf key into the join filter was tried and dropped: it also moved keys DataFusion would have placed, and the next pass's `extract_equijoin_predicate` fought it. The affected shape now runs as a nested-loop join over the same cross product the buggy plan built, with the missing filter applied. The tripwire `plain_datafusion_still_drops_the_key` fails once DataFusion fixes #26058; then delete the copy. Upstream PR not filed.
