**STATUS 2026-09-16 (av): storage credentials that expire say so, and are not frozen into the process (`fix/storage-credentials-expiry`).** After a few hours every scan on a Glue-backed table failed with `Object Store error: Generic S3 error: an error occurred while loading credentials` while `SELECT 1` still worked. Two findings. The refreshing provider already existed: with no static key, S3 stores read through the AWS SDK default chain (`aws_config::sdk_object_store_credentials`), which caches and refreshes for as long as the SSO or role session that issued the credentials lasts; that message is the chain saying the session itself ended. The trap was the environment path: `AWS_ACCESS_KEY_ID` + `AWS_SESSION_TOKEN` (the `export-credentials` recipe the docs showed) were pinned into `[storage]` as static keys at startup, session token included, and expired on a clock nobody could see. Now: temporary env keys are not pinned (the SDK chain reads the same environment while valid; `AWS_PROFILE` gets refresh), a static key with a session token under `[storage]` warns at startup; the SDK bridge renders `storage credentials expired or unavailable (aws sdk default chain): <chain>` with the remedy and `sqe-core` classifies that text and S3's `ExpiredToken` / `InvalidAccessKeyId` / "security token ... invalid" replies as `STORAGE_CREDENTIALS_UNAVAILABLE` (65605, Trino `EXTERNAL`, gRPC `Unauthenticated`), ahead of the 403 patterns that used to make it look like the user's grant; and the MCP `list_catalogs` diagnostics gain an `object_store` entry (`provider`, `status` ok/auth_error/unknown/timeout, `expires_at` when the SDK knows it) from a probe the coordinator wires from `[storage]`, so the sidecar checks before a long job. Tests: env adoption (permanent pinned, temporary not), the message, the classification, the MCP entry. Docs on three pages. Same branch, same cause: `describe_schema` over 25 Hive tables hung indefinitely with `include_stats` or `include_queryability` on (0.4 s with both off) because a stats or plan probe on a table whose storage credentials had expired waited instead of failing; every per-table statement now has a 20 s deadline (`DESCRIBE_SCHEMA_PROBE_TIMEOUT`) and a timed-out probe lands on that table's `stats_error` / `queryability_error` with a pointer to the diagnostics, and the SDK credential resolution itself is bounded at 10 s (`CREDENTIAL_RESOLVE_TIMEOUT`) so a chain that hangs becomes the same `STORAGE_CREDENTIALS_UNAVAILABLE`. A hang test in the `describe_schema` fixture (a probe that never answers, paused tokio clock) pins it.
