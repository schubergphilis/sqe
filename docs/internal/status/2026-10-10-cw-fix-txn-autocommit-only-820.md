**STATUS 2026-10-10 (cw): autocommit-only transactions over Trino and Flight SQL (`fix/txn-autocommit-only-820`, #820).** `BEGIN` / `COMMIT` / `ROLLBACK` were no-op stubs, so a JDBC client that called `setAutoCommit(false)` was told it had a transaction while every write committed on its own, and `ROLLBACK` undid nothing. SQE now follows Trino's Iceberg connector. `START TRANSACTION` hands out a transaction id: in `X-Trino-Started-Transaction-Id` over Trino (the client echoes it in `X-Trino-Transaction-Id`, and `COMMIT` / `ROLLBACK` answer `X-Trino-Clear-Transaction-Id`), or on the stored session over Flight SQL. Inside the transaction reads, session statements and transaction control run, and anything else fails before planning with `AUTOCOMMIT_WRITE_CONFLICT` (Trino code 25, "Catalog only supports writes using autocommit: <catalog>"). That check sits in one place, `execute_inner`, so it also covers a prepared write run through `EXECUTE`. `StatementKind::allowed_in_transaction` is an allow-list, so a new statement kind is refused by default, and the `Utility` bucket names its statements too (an `ALTER TABLE ... OWNER TO` lands there). Over Flight SQL the transaction lives on the token's session, like `USE`: a client that sends `BEGIN` and disconnects leaves writes on that token refused until `COMMIT` / `ROLLBACK` or session expiry. A nested `BEGIN`, `SNAPSHOT` isolation, savepoints and `BEGIN ... END` blocks are refused, and `SET TRANSACTION` is accepted. Flight SQL still advertises `SQL_SUPPORTED_TRANSACTION_NONE` with no `BeginTransaction` RPC. Tests: classifier, Trino server header round-trip, and a coordinator guard test. Stacked on the dbt-sqe change, which must land first. **NEXT:** a live JDBC `setAutoCommit(false)` run against the Trino endpoint.
