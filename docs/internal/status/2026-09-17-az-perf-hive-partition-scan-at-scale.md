**STATUS 2026-09-17 (az): a LIMIT over a thousand-partition snapshot table reads one partition, and a query no longer outlives its caller (`perf/hive-partition-scan-at-scale`, #685 #686).** The Glue crawl's mcp.log showed four statements on `afas_raw.mgtinfo_ledger` (548k objects, 551 GB, 1,241 daily `snapshot_date` projected partitions) and `mgtinfo_accounts` (1,590 partitions) failing with "Query timed out after 300s" after 21 to 27 minutes each, retried by the sidecar so two ran side by side, RSS 335 MB to 1.8 GB. Three causes, all in the scan path, none in the data: `scan_from_entries` built one `ListingTable` per surviving partition at plan time and sequentially (each build lists the prefix, 0.65 s from this laptop, so 17 minutes before the first row); `EngineHiveDataStoreFactory::store_for` built a fresh S3 store per partition, and with no static key that is a fresh SDK credential chain loading the profile and resolving the SSO session 1,241 times per query (also the blocking work that starved the 300 s timer); and the plan held every partition's file metadata. Now: `LazyPartitionScanExec` takes a pushed-down LIMIT over more than one partition, sorts entries descending (newest first, the useful answer for a snapshot table and one a bare LIMIT never promised otherwise), builds and reads each partition's scan at execute time through the shared `plan_partition_scan`, and stops when the limit is met; the unlimited path and the worker-task listing run sixteen partition listings in flight instead of one after another; the factory caches one store per (bucket, secret) for five minutes. Provider test on the counting store: `LIMIT 1` over two projected partitions lists exactly one, `LIMIT 2` continues into the second, `count(*)` still reads all. Coordinator side: `mcp.request_timeout_secs` (default 75, below the ~90 s an MCP client waits before retrying) drops the statement's future past the deadline and reports it with the two ways out; `AbandonedQueryGuard` in `execute_inner` moves a dropped query's tracker record to Canceled/QUERY_ABANDONED and fires its cancel token, so a disconnected caller no longer leaves a "running" query for hours; `QueryTracker::finish` drops the second verdict the timeout arm and the shared error path both recorded, so a failure is logged once. Gotcha for the next reader: a `StreamExt::map` closure returning `async move` over a borrowed entry compiles in the catalog crate and breaks the coordinator's `Send` proof ("implementation of `Send` is not general enough"); build the futures with `Iterator::map` first and hand the Vec to `stream::iter(..).buffered(..)`. Measured against live Glue with the final release build beside the old server: `SELECT * FROM mgtinfo_accounts LIMIT 10` 21 min → 6.8 s cold, 1.4 s warm, `EXPLAIN` shows `LazyPartitionScanExec: partitions=2270, limit=10, order=newest-first`; `mgtinfo_ledger LIMIT 5` (gz JSON, 548k objects) 0.7 s; an unlimited `count(*)` over the ledger listed all 1,241 partitions in about 20 s (was 13 min of listing alone) and then failed honestly on a 2023 object in GLACIER storage class, which is the table's state, not the engine's; `count(*) WHERE snapshot_date >= DATE '2026-01-01'` (260 partitions, ~110 GB gz JSON) hit the MCP deadline at 80 s with the tracker record `CANCELED / QUERY_ABANDONED` and nothing left running, RSS 3.3 GB at that point (the eager plan holds 260 partitions' file metadata plus decode buffers; a lever for later). Zero 429s in the new build's log across all of it. The live run found two more causes under the first three. (4) The SDK default chain does not cache credentials when called outside an SDK client (aws-config 1.x moved the cache into the service client's identity resolver), so `SdkObjectStoreCredentials` asked the SSO portal for role credentials on EVERY S3 request; sixteen partition listings in flight answered `TooManyRequestsException: HTTP 429` within seconds, surfacing as "storage credentials expired". Now cached single-flight until five minutes before expiry (fifteen minutes without one); unit tests count one resolution for 32 concurrent callers. The old server still running beside the new one keeps flooding the portal until it is restarted, and its 429s hit the new build too. (5) `detect_compression` recorded a FAILED listing (that 429) as "uncompressed" in the facts cache, so a gzipped JSON table failed for the next minute as `Encountered unexpected ''` from the JSON parser; a failed probe now records nothing and the next lookup probes again (provider test with a store that fails one listing). What the crawler should know is now in the engine (newest partition first), so the sidecar needs no snapshot-aware logic for `sample_rows`; `describe_schema` could still expose partition keys so a profile can say "one day of 1,241".
