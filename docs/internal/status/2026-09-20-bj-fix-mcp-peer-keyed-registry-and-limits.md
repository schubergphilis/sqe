**STATUS 2026-09-20 (bj): MCP client registry and query rate limit are keyed on the caller's address as well as the user (`fix/mcp-peer-keyed-registry-and-limits`, #680; #676 analysed, left open).** Third of the MCP security batch. In `static` and `anonymous` mode every caller is one configured user, so the `Mcp-Session-Id` binding (user only) let one client relabel another's audit trail by replaying an observed id, and the per-user query limit was one shared global any single client could spend. `Session` gains `peer_ip` (set by MCP `authenticate` in every mode), `ClientSession` binds `(user, peer)` and `label`/`remove` check both, and `CoordinatorMcpExecutor` keys the query limiter on `peer|user`. No X-Forwarded-For handling was added: behind a proxy every caller shares the proxy address, which is today's behaviour, not a regression; trusted-proxy config is a follow-up if a proxied static deployment appears. #676 (scopes from an unverified decode): no introspection provider exists and `bearer_token` verifies the very JWT the decode reads, so there is no path where an opaque token passes the provider and 403s here; carrying scopes on `Identity` touches ~80 struct literals for a consumer that does not exist. Left open with that analysis for the provider that needs it. Tests: `the_same_principal_from_another_address_cannot_borrow_a_session_id`, `sessions_carry_the_peer_address_for_the_rate_limit_key`. Verified: workspace `cargo check`, sqe-mcp unit suite, clippy on the touched crates.
