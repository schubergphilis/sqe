**STATUS 2026-11-04: a reader's DELETE / UPDATE / MERGE / TRUNCATE is refused before any file is written (`fix/dml-write-precheck`, #880 part 1).**

`SessionCatalog::check_write_access` runs in `dispatch_delete_on`, `dispatch_update_on` and `dispatch_merge_on` right after the target loads, on REST catalogs that vend credentials only. It posts a commit that changes nothing: `assert-table-uuid` and `assert-ref-snapshot-id main` with `set-snapshot-ref main` set to the same reference, or requirements only when there is no `main` or the ref moved (409). Polaris 1.7 authorizes per update (`SET_TABLE_SNAPSHOT_REF`, or `UPDATE_TABLE` for the empty list) and answers a reader 403; `CatalogHandlerUtils` skips the commit when nothing changed, so a writer's metadata location and snapshot count stay as they were. Verified against Polaris 1.7.0 + Ranger 2.8 on the portal-data stack (analyst 403 on both forms, engineer and admin 200 with metadata unchanged) and in `dml_write_precheck_e2e` (a `TABLE_READ_DATA`-only principal is refused all four statements, the object listing under the table location is unchanged, root's DELETE still commits). Only a 403 refuses; every other error logs a warning and the real commit decides.

Limits: a principal with `TABLE_WRITE_PROPERTIES` (or `TABLE_FULL_METADATA`) but not `TABLE_WRITE_DATA` passes the check, gets read-only keys and still fails at `PutObject` (reported as `ACCESS_DENIED` since !1644). The fallback paths taken when the target cannot be resolved or loaded skip the check. INSERT / CTAS are not checked. Other vending REST catalogs (Databricks UC) were not probed; on them a non-403 answer leaves today's behaviour.

The issue suggested a `loadTable` with write delegation; that cannot refuse: Polaris 1.7 `authorizeLoadTable` falls back from `LOAD_TABLE_WITH_WRITE_DELEGATION` to read delegation on a `ForbiddenException`, so a reader still gets 200 and read-only keys. With !1644 (object-store 403 as `ACCESS_DENIED`) this closes #880.
