**STATUS 2026-10-10 (cy): multi-table atomic COMMIT (`feat/txn-multi-table-823`, #823).** A transaction may now write several tables in one catalog. Each table keeps its own `sqe-txn-<id>` branch; `COMMIT` prepares one `PublishBranchAction` per table (new vendored `Transaction::prepare_commit`) and sends them in one `Catalog::commit_transaction` (new vendored trait method). REST posts to `/v1/{prefix}/transactions/commit` (Polaris); the embedded SQLite catalog swaps every pointer in one `BEGIN IMMEDIATE`. A requirement failure on any table is `TRANSACTION_CONFLICT` and drops every branch; neither table moves. Admission is at write time (`txn::admit`), before any file is written: a second catalog is refused, and a second table is refused on a catalog that cannot commit atomically (a REST server not advertising the route, Glue, Hive). A REST 404 is `TableNotFound` only when the body names `NoSuchTable`, otherwise unsupported. **#821 fix found by the Polaris test:** in a multi-thread runtime, a SELECT (and a DML source query) inside a transaction read `main`, not the branch, because `on_planning_stack` polls planning on its own thread, where the task-local transaction scope is unset; `txn::carried` now captures it at all five call sites. The sqlite-rig tests missed it because `#[tokio::test]` is current-thread, where the planning stack runs inline. Tests: five vendored REST tests, SQLite `swap_pointers` rollback test, three sqlite-rig transaction tests in `sqe-write`, admission unit tests, two Polaris integration tests (commit, conflict aborts both). **NEXT:** a live JDBC `setAutoCommit(false)` run with writes to two tables.
