**STATUS 2026-09-16 (as): an expired AWS session says so (`fix/glue-credential-errors`).** When the engine's credentials for a Glue root lapse, `list_schemas` answered `hive_external: object store error: glue get_databases failed: dispatch failure`: the SDK's `Display` is the bare error kind and the reason ("no credentials", "the SSO session has expired") sits two levels down its `source()` chain. `GlueMetadataSource` now classifies every failed call: a `DispatchFailure` whose chain talks about credentials, a token, SSO or a provider, or a signed request STS rejects (`UnrecognizedClientException`, `InvalidSignatureException`, `ExpiredTokenException`, `InvalidClientTokenId`), becomes `HiveError::Credentials` reading `AWS credentials missing or expired for the Glue catalog (region=eu-central-1, op=get_databases: ...)` with the remedy; every other failure keeps the operation name and the full chain instead of "dispatch failure". `AccessDeniedException` stays a permission error on purpose. The MCP `list_catalogs` tool adds `diagnostics`: one entry per visible Hive root probed with `SHOW SCHEMAS` (concurrent, 5 s bound) as `reachable` / `auth_error` / `timeout` / `unreachable` with the detail, so the sidecar's journey page can say "the catalog is fine, the engine's credentials are not". Also verified: a scan with unusable S3 keys fails loudly (`403 InvalidAccessKeyId` on the LIST, planning error), on the `read_parquet` path at least; the silent-zero shape from 2026-09-02 (sidecar bridge, expired session token) did not reproduce with invalid static keys and stays open until a real expiry is caught with `RUST_LOG=debug`.
